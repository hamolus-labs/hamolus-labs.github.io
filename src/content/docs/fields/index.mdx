A **field definition** describes one column of a collection. Hamolus turns that
single object into **three things at once**:

| Output | What it does |
| ------ | ------------ |
| **DDL column** | Physical D1 column (`TEXT` / `NUMERIC` / `INTEGER`) |
| **Zod validator** | Enforced on every record write |
| **Console UI** | Form widget + table cell, chosen by `type` and `control` |

Fields never exist on their own — they live inside a collection's `fields` array,
whether you write that array in the console, over HTTP, or in TypeScript.

```ts
// core/src/collections/posts.ts  (code-defined)
import type { CollectionDefinitionInput } from '@hamolus/types'

export const POSTS = {
  name: 'posts',
  label: 'Posts',
  primaryKey: 'id',
  fields: [
    { name: 'title', type: 'string', label: 'Title', required: true },
    { name: 'slug', type: 'slug', label: 'Slug', required: true, unique: true },
    { name: 'published', type: 'boolean', label: 'Published', default: false },
  ],
} satisfies CollectionDefinitionInput
```

```jsonc
// PUT /api/_meta/collections/posts   — identical shape
{
  "name": "posts",
  "label": "Posts",
  "fields": [
    { "name": "title", "type": "string", "label": "Title", "required": true },
    { "name": "slug", "type": "slug", "label": "Slug", "required": true, "unique": true },
    { "name": "published", "type": "boolean", "label": "Published", "default": false }
  ]
}
```

## Three audiences for the same object

```
              FieldDefinition
                     │
     ┌───────────────┼────────────────┐
     ▼               ▼                ▼
  Database       API / Zod        Admin console
  DDL + coerce   validation       FieldEditor → RecordForm → Table
```

That is why the same property can mean different things in different places:

- `required: true` → `NOT NULL` in DDL **and** a write-time check
  (unless `default` is also set — then write-time is optional)
- `control: 'radio'` → no effect on storage; only changes the record form widget
- `consoleView: 'side'` → no effect on storage; only moves the field in the form
  layout
- `localized: true` → storage becomes `{ locale: value }` **only** on six types

## Validation at a glance

`.strict()` — unknown keys are errors, not silent no-ops.

Cross-field refinements the schema enforces:

1. `type: 'enum'` ⇒ `enumValues` present and non-empty
2. `format` only on `richtext`
3. `control` only on `boolean` / `enum` / `relation` (and only allowed values)
4. `currency` only on `currency`
5. `customCurrency` only on `custom_currency`

## Current platform gaps (by design today)

- `indexed` is **metadata only** — no `CREATE INDEX` is emitted
- `onDelete` on relations is **metadata only** — no cascade/restrict in D1
- `email` / `url` do not validate format (render hints)
- `localized` is inert outside the six types that honour it
- `PUT` only **adds** columns — no rename, retype or drop via the API
